## 1. Выбор данных для шардирования

1. **Какую сущность вы выбрали?** Задачи — таблицу `tasks`. Это самая большая и быстрее всех растущая таблица сервиса: миллион строк против 10 тысяч пользователей и тысячи проектов. Именно её объём упирается в возможности одного сервера, остальные таблицы маленькие и остаются в основной базе.

2. **Какое поле используется как shard key?** `user_id` — владелец задачи.

3. **Почему выбран именно этот ключ?**
   - почти все запросы сервиса к задачам выполняются в контексте пользователя: список своих задач, создание, статистика, проверка прав;
   - все задачи одного пользователя оказываются на одном шарде, поэтому его список читается одним запросом к одному серверу, без сбора данных со всех шардов;
   - ключ не меняется: задача не переходит к другому владельцу, значит запись никогда не переезжает из-за изменения ключа;
   - `user_id` — UUID, после хэширования он даёт равномерно распределённые значения.

   Отклонённые варианты: `id` задачи распределил бы строки идеально, но список задач пользователя пришлось бы собирать со всех шардов; `project_id` может быть пустым; `created_at` сложил бы всю свежую нагрузку на один шард.

4. **Насколько равномерно он будет распределять данные?** По числу пользователей — практически равномерно: хэш от UUID ведёт себя как случайное число. По числу задач — хуже, потому что пользователи неодинаковы: медиана 72 задачи на пользователя, 99-й перцентиль — 502, а у самого активного `gen_user_1` — 9 900 задач, почти 1 % всей таблицы. Такого пользователя нельзя разрезать между шардами, он целиком лежит на одном — это «горячий ключ».

5. **Какие запросы сервиса используют этот ключ?**

<!-- caption: Запросы сервиса и shard key -->
| Запрос | Использует `user_id` | На сколько шардов идёт |
|---|---|---|
| `GET /api/tasks` пользователя — список своих задач | да, `WHERE user_id = …` | 1 |
| `POST /api/tasks` — создание задачи | да, владелец известен из токена | 1 |
| `GET /api/tasks/stats` для пользователя | да | 1 |
| Проверка владельца задачи (`IsOwnerAsync`) | да, если известен владелец | 1 |
| `GET /api/tasks/{id}` без владельца | нет | все шарды |
| Список всех задач администратора, статистика по всем | нет | все шарды |

## 3. Реализация простого Router

### Хэш-функция

Router должен давать один и тот же ответ в любом процессе и на любой машине. Стандартный `GetHashCode()` в .NET для этого не годится: он случайный для каждого запуска процесса. Поэтому используется MD5 от строкового вида `user_id`, а первые 8 байт дайджеста дают 64-битное число:

<!-- caption: Стабильный хэш ключа -->
```csharp
public static ulong Of(string key)
{
    Span<byte> digest = stackalloc byte[MD5.HashSizeInBytes];
    MD5.HashData(Encoding.UTF8.GetBytes(key), digest);
    return BitConverter.ToUInt64(digest[..8]);
}
```

MD5 здесь не защищает данные, а только перемешивает биты, поэтому его криптографическая слабость не имеет значения.

### shard = hash(shard_key) % N

<!-- caption: Router hash(key) % N -->
```csharp
public sealed class ModuloShardRouter : IShardRouter
{
    public ModuloShardRouter(int shardCount) => ShardCount = shardCount;

    public ShardStrategy Strategy => ShardStrategy.Modulo;

    public int ShardCount { get; }

    public int GetShard(Guid key) => (int)(ShardHash.Of(key) % (ulong)ShardCount);
}
```

<!-- caption: Самые тяжёлые пользователи каждого шарда -->

**Выводы.**
- **Насколько равномерно.** Практически идеально: доли шардов 32.7–33.8 % при идеале 33.3 %, разница между крайними шардами 1.1 процентного пункта. Хэш от UUID равномерен, а 10 000 ключей достаточно, чтобы случайные отклонения сгладились.
- **Есть ли заметный дисбаланс.** По записям — нет. Но дисбаланс сидит внутри: самый активный пользователь `gen_user_1` целиком лежит на Shard 2 и один даёт ему 9 900 задач. Сейчас это 3 % шарда, и общую картину он не портит.
- **Может ли дисбаланс стать проблемой.** Да, в двух случаях. Во-первых, если один пользователь (или организация) вырастет до заметной доли всех данных: его нельзя разрезать, и шард, на котором он живёт, будет больше и нагруженнее остальных, сколько бы шардов мы ни добавили. Во-вторых, равное число строк не означает равную нагрузку: активный пользователь делает больше запросов, поэтому по CPU шард может быть перегружен даже при одинаковом объёме данных.

## 5. Что произойдёт при добавлении нового shard

К системе добавляется четвёртый экземпляр: вместо `hash(key) % 3` теперь `hash(key) % 4`. Для каждого из 10 000 пользователей сервис вычислил шард до и после изменения и сложил задачи тех, у кого шард поменялся.

<!-- caption: Переход hash(key) % 3 → hash(key) % 4 -->
| Показатель | Значение |
|---|---|
| Всего записей | 1 000 000 |
| Новый шард | Shard 3 |
| Изменили shard | 753 446 |
| Не изменили | 246 554 |
| Перемещено | **75.34 %** |
| Пользователей переехало | 7 516 из 10 000 |

<!-- caption: Куда уходят задачи при hash % 3 → hash % 4 -->
| Откуда \ Куда | Shard 0 | Shard 1 | Shard 2 | Shard 3 |
|---|---|---|---|---|
| Shard 0 | — | 83 919 | 80 820 | 82 350 |
| Shard 1 | 86 879 | — | 85 954 | 78 915 |
| Shard 2 | 93 824 | 77 682 | — | 83 103 |

**Почему добавление одного PostgreSQL требует перемещения большого объёма данных.** Номер шарда — это остаток от деления хэша на N, и при смене N остаток меняется почти у всех ключей. Ключ остаётся на месте, только если `hash % 3 == hash % 4`, то есть если `hash % 12` равен 0, 1 или 2 — это 3 случая из 12, ровно 25 %. Остальные 75 % ключей переезжают, что и показал замер: 75.34 %.

Главное — матрица переносов. Данные не просто уезжают на новый шард: старые шарды массово обмениваются задачами между собой (0 → 1, 1 → 2, 2 → 0…), хотя на них ничего не изменилось. Новому шарду нужна четверть данных, а переезжают три четверти. На время переноса это нагрузка на все серверы сразу и долгое окно, когда часть задач уже переехала, а часть ещё нет.

## 6. Реализация Consistent Hashing

### Как устроено кольцо

Хэши занимают диапазон от 0 до 2⁶⁴ − 1; замкнём его в кольцо, где после максимума снова идёт 0.

1. Каждый шард ставит на кольцо свои точки — **виртуальные узлы**. Точка — хэш строки `shard-{номер}#vnode-{номер узла}`, поэтому её положение зависит только от номера шарда и узла и не зависит от того, сколько всего шардов.
2. Ключ хэшируется в точку на том же кольце.
3. Ключ принадлежит шарду, чья точка первая по часовой стрелке от точки ключа. Если дальше точек нет, поиск продолжается с начала кольца.

Точки хранятся в отсортированном массиве, поэтому поиск двоичный: около 11 сравнений для трёх шардов по 500 узлов.

<!-- caption: Hash ring с виртуальными узлами -->
```csharp
public ConsistentHashRouter(int shardCount, int virtualNodes = 100)
{
    var ring = new List<(ulong Point, int Shard)>(shardCount * virtualNodes);
    for (var shard = 0; shard < shardCount; shard++)
    {
        for (var node = 0; node < virtualNodes; node++)
        {
            ring.Add((ShardHash.Of($"shard-{shard}#vnode-{node}"), shard));
        }
    }

    ring.Sort((a, b) => a.Point.CompareTo(b.Point));
    _points = ring.Select(r => r.Point).ToArray();
    _owners = ring.Select(r => r.Shard).ToArray();
}

public int GetShard(Guid key)
{
    var index = Array.BinarySearch(_points, ShardHash.Of(key));
    if (index < 0)
    {
        index = ~index;              // первая точка больше хэша ключа
    }

    return _owners[index == _points.Length ? 0 : index];   // за последней точкой — снова начало кольца
}
```

Главное свойство следует из первого пункта: кольцо для N + 1 шардов — это кольцо для N шардов плюс точки нового шарда. Точки старых шардов остаются на местах, поэтому ключ может сменить шард только в одном случае — если между ним и его прежней точкой встала точка нового шарда.

### Распределение на кольце

<!-- caption: Распределение задач через hash ring, 3 шарда, 100 виртуальных узлов (SQL на шардах) -->
| Шард | Задач | Пользователей | Доля задач |
|---|---|---|---|
| Shard 0 | 304 908 | 3 026 | 30.49 % |
| Shard 1 | 303 844 | 2 922 | 30.38 % |
| Shard 2 | 391 248 | 4 052 | 39.12 % |

Кольцо со 100 виртуальными узлами распределило данные заметно хуже, чем `hash % 3`: Shard 2 получил 39 % задач, в 1.174 раза больше среднего. Дело не в тяжёлых пользователях — перекос такой же по их числу (4 052 против 2 922), — а в том, как случайно легли точки: дуги кольца, доставшиеся шарду 2, в сумме оказались длиннее. Как это лечат виртуальные узлы — в разделе 7.

## 7. Сравнение стратегий

### 3 → 4 шарда

<!-- caption: Перенос данных при добавлении четвёртого шарда -->
| Стратегия | Перемещено задач | Перемещено пользователей | Куда уходят задачи |
|---|---|---|---|
| `hash(key) % N` | **75.34 %** (753 446) | 7 516 | на все шарды, включая старые |
| Consistent Hashing, 100 узлов | **24.09 %** (240 903) | 2 444 | только на Shard 3 |
| Consistent Hashing, 500 узлов | **27.35 %** (273 461) | 2 668 | только на Shard 3 |

<!-- caption: Потоки задач при 3 → 4 на hash ring (100 узлов) -->
| Откуда | Куда | Задач |
|---|---|---|
| Shard 0 | Shard 3 | 76 922 |
| Shard 1 | Shard 3 | 68 713 |
| Shard 2 | Shard 3 | 95 268 |

**1. Почему результаты отличаются.** В `hash % N` число шардов входит в формулу для каждого ключа, поэтому при изменении N расположение пересчитывается у всех ключей и совпадает случайно лишь у четверти. В consistent hashing ключ привязан не к N, а к ближайшей точке на кольце. Добавление шарда добавляет точки, но не сдвигает существующие, поэтому у большинства ключей ближайшая точка остаётся прежней.

**2. Почему consistent hashing уменьшает объём переноса.** Переезжают только ключи, попавшие на дуги перед новыми точками, и все они едут на новый шард. Обмена между старыми шардами нет. Новому шарду нужна примерно 1/(N + 1) данных — при 3 → 4 это 25 %, — и примерно столько и переносится: 24.1 % при 100 узлах, 27.4 % при 500. Точное значение зависит от того, какую долю кольца получил новый шард.

**3. Что произойдёт, если добавить ещё один шард.**

<!-- caption: Последовательное добавление шардов -->
| Изменение | `hash % N` | Consistent Hashing, 100 узлов | Доля, нужная новому шарду |
|---|---|---|---|
| 3 → 4 | 75.34 % | 24.09 % | 25.0 % |
| 4 → 5 | 79.41 % | 20.06 % | 20.0 % |
| 5 → 6 | 83.90 % | 13.77 % | 16.7 % |

С ростом числа шардов `hash % N` становится только хуже: на месте остаются лишь ключи с совпадающими остатками, их доля стремится к 1/(N + 1). Consistent hashing, наоборот, переносит всё меньшую долю — примерно столько, сколько забирает себе новый шард.

**4. Что произойдёт, если удалить шард.**

<!-- caption: Удаление шарда -->
| Изменение | `hash % N` | Consistent Hashing, 100 узлов |
|---|---|---|
| 4 → 3 | 75.34 % | 24.09 % — только данные удалённого Shard 3 |
| 3 → 2 | 67.70 % | 39.12 % — ровно содержимое Shard 2 |

При удалении шарда из кольца исчезают его точки. Его ключи достаются следующим по кольцу точкам разных оставшихся шардов (76 922 задачи уходят на Shard 0, 68 713 — на Shard 1, 95 268 — на Shard 2), а ключи остальных шардов не двигаются вовсе. `hash % N` снова перетасовывает почти всё. Удаление Shard 2 из трёх переносит в кольце 39 % — это не недостаток алгоритма, а размер удаляемого шарда: переносится ровно то, что на нём лежало.

| 1 | 2.451 | 103.13 % | 77.48 % |

Для сервиса выбрано 500 узлов: перекос около 2 % при переносе, близком к идеальным 25 %.

## Проверка: настоящий перенос данных

Прогноз проверен на живых данных. Сервис переведён на hash ring с 500 узлами, запущен четвёртый PostgreSQL, и сервис перенёс задачи командой `POST /api/shards/rebalance?shards=4`.

Перенос идёт пачками по 500 пользователей. Задачи копируются на новый шард через `COPY` во временную таблицу и `INSERT … ON CONFLICT DO NOTHING`, и только после фиксации копии удаляются с исходного шарда. Общей транзакции у двух баз нет, поэтому порядок шагов выбран так, чтобы сбой в середине оставил дубликат, но не потерю; повторный запуск дубликат уберёт. Топология в основной базе переключается только после того, как данные на месте.

Прогноз совпал с реальностью до задачи. Пользователь `gen_user_3` до переноса читался с Shard 0, после — с Shard 3, после удаления шарда — снова с Shard 0, и во всех трёх случаях сервис вернул все его 3 136 задач.

## Вопросы для самопроверки

1. **Что такое shard?** Отдельный экземпляр базы данных — со своими ресурсами сервера, диском и процессами, — который хранит часть данных общей логической таблицы. В работе это три контейнера `postgres-shard-0…2`, каждый с собственным кластером PostgreSQL и своей долей задач.

2. **Что такое shard key?** Поле записи, по которому router определяет её шард. От него зависят равномерность распределения, какие запросы идут на один шард, а какие на все, и придётся ли переносить запись при изменении данных. В работе это `user_id`.

3. **Почему нельзя просто случайно распределять записи между PostgreSQL?** Потому что запись потом нужно найти. При случайном размещении шард записи нигде не зафиксирован, и любой запрос — даже чтение одной задачи — пришлось бы отправлять на все шарды. Либо пришлось бы вести отдельную таблицу «запись → шард», которая сама становится узким местом. Кроме того, связанные данные — все задачи одного пользователя — разлетелись бы по разным серверам. Детерминированная функция от shard key позволяет вычислить шард, ничего не спрашивая у базы.

4. **Как работает hash(key) % N?** Хэш-функция превращает ключ в большое число — в работе это первые 8 байт MD5 от `user_id`. Остаток от деления этого числа на количество шардов N даёт номер шарда от 0 до N − 1. Хорошая хэш-функция делает остатки равновероятными, поэтому данные делятся почти поровну: 32.66 / 33.55 / 33.79 %.

5. **Почему изменение количества shard'ов является проблемой?** Потому что N входит в формулу каждого ключа. После смены N у большинства ключей остаток становится другим, и их данные лежат не там, где их будет искать router. Перед переключением эти данные нужно перенести: при 3 → 4 это 75 % задач (753 446 из миллиона), при 5 → 6 — уже 84 %. Перенос нагружает все шарды, занимает время и создаёт окно, когда часть данных уже на новом месте, а часть ещё на старом.

6. **Что такое Consistent Hash Ring?** Способ маршрутизации, при котором пространство хэшей замыкается в кольцо. Каждый шард ставит на кольцо свои точки, ключ хэшируется в точку на том же кольце и принадлежит шарду, чья точка ближайшая по часовой стрелке. В реализации сервиса поиск шарда — двоичный поиск по отсортированному массиву точек.

7. **Почему при добавлении shard'а не приходится переносить все данные?** Положение точек существующих шардов не зависит от числа шардов, поэтому при добавлении нового они не сдвигаются. Новый шард лишь добавляет свои точки, и шард меняется только у ключей, для которых новая точка оказалась ближе прежней. Все такие ключи переезжают на новый шард — примерно 1/(N + 1) данных. В работе при 3 → 4 это 24–27 %, и ни одна задача не переехала между старыми шардами.

8. **Что такое virtual nodes и зачем они нужны?** Виртуальные узлы — несколько точек на кольце для одного физического шарда. С одной точкой на шард кольцо делится на несколько случайных дуг разной длины, и шарды получают очень разные доли: в замере один из трёх шардов получил в 2.45 раза больше среднего. Когда у шарда сотни точек, его доля складывается из многих маленьких дуг и приближается к равной: при 500 узлах перекос около 2 %. Ещё виртуальные узлы делают перенос мягче: новый шард забирает понемногу у всех, а данные удалённого шарда расходятся по всем оставшимся, а не достаются одному соседу. А меняя число узлов, можно дать более мощному серверу больше данных.

9. **Может ли Consistent Hashing гарантировать идеальное распределение нагрузки?** Нет. Во-первых, даже по числу ключей распределение только приблизительно равное и зависит от случайного положения точек: 100 узлов в работе дали 39 % на одном шарде из трёх. Во-вторых, алгоритм распределяет ключи, а не нагрузку: пользователь с 9 900 задачами и пользователь с одной задачей для него одинаковы, и «горячий» ключ целиком лежит на одном шарде. В-третьих, нагрузка определяется не только объёмом данных, но и частотой запросов. Consistent hashing решает проблему переноса данных, а не проблему равномерности.

10. **Что произойдёт, если один shard станет значительно более загруженным остальных?** Он станет узким местом всей системы: запросы пользователей этого шарда будут медленнее, а при исчерпании диска или CPU перестанут обслуживаться, хотя остальные шарды простаивают. Простое добавление шарда помогает лишь частично: новый шард заберёт часть ключей, и не обязательно у перегруженного. Решение зависит от причины. Если неудачно легли точки — поменять число виртуальных узлов. Если виноват один горячий ключ — вынести его на выделенный шард или сделать ключ составным, например `user_id` и проект. Если перегрузка по чтению — добавить этому шарду реплики, как в ЛР № 4. Во всех случаях перекос нужно замечать заранее, поэтому размер и нагрузку шардов надо мониторить так же, как отставание реплики.

## 8. Итог

Shard — это отдельный экземпляр базы данных, который хранит часть общих данных: у каждого шарда своё подмножество строк, а вместе шарды содержат всё. Shard key — поле, по которому определяется, на каком шарде лежит запись; в TaskManager это `user_id`, поэтому все задачи пользователя живут на одном шарде и читаются одним запросом. Router — компонент сервиса, который по shard key решает, к какому PostgreSQL обратиться: без него приложение не знало бы, где искать запись, и опрашивало бы все шарды. Стратегия `hash(key) % N` берёт остаток от деления хэша ключа на число шардов; она проста и распределяет данные почти идеально — 32.7–33.8 % на трёх шардах. Её проблема — изменение N: остаток пересчитывается у всех ключей, и при переходе с трёх шардов на четыре переезжают 75 % задач, причём старые шарды массово обмениваются данными между собой. Consistent hashing размещает шарды точками на кольце хэшей, и новый шард лишь добавляет свои точки, не сдвигая чужие: переезжает только то, что достаётся новому шарду, — 24–27 % вместо 75 %, и всё это идёт на новый шард. Платой за это становится равномерность: при малом числе виртуальных узлов кольцо даёт перекос (39 % на одном шарде при 100 узлах), который уходит при сотнях узлов. Для TaskManager выбран consistent hashing с 500 виртуальными узлами: сервис растёт, шарды придётся добавлять, и перенос четверти данных вместо трёх четвертей определяет длительность окна миграции, а перекос около 2 % на такой конфигурации несущественен. Настоящий перенос на четвёртый PostgreSQL совпал с расчётом до задачи — 273 461 задача за 8 секунд.
