## 1. Архитектура после шардирования

После ЛР № 4 и № 5 сервис работает уже не с одной базой, а с пятью экземплярами PostgreSQL. Router находится внутри сервиса: по `user_id` он выбирает шард для задач, а всё остальное идёт в основную базу или её реплику.

<!-- caption: Архитектура TaskManager после шардирования -->
```
                               Backend (TaskManager API)
                                         │
              ┌──────────────────────────┼──────────────────────────────┐
              │                          │                              │
     users, projects, tags,       Router: hash ring(user_id)      чтение списков
     task_tags, топология                │                          (ЛР № 4)
              ▼               ┌──────────┼──────────┐                   ▼
       Основная база          ▼          ▼          ▼            Replica основной
       (Primary, 5432)     Shard 0    Shard 1    Shard 2          базы (5433)
                           (5440)     (5441)     (5442)
                            tasks      tasks      tasks
```

Из этого сразу видно, какие запросы будут простыми: те, что знают `user_id` и касаются только задач, идут на один шард. Всё остальное — запросы по всем задачам и запросы, которым вместе с задачами нужны проекты, пользователи или теги, — становится распределённым.

## 2. Single-Shard Query

**Запрос сервиса.** Список задач пользователя — `GET /api/tasks` от имени пользователя, метод `TaskRepository.GetByUserIdAsync`:

<!-- caption: Запрос списка задач пользователя -->
```sql
SELECT t.id, t.created_at, t.description, t.due_date, t.priority, t.project_id, t.status, t.title, t.updated_at, t.user_id
FROM tasks AS t
WHERE t.user_id = $1
ORDER BY t.created_at DESC
LIMIT $2 OFFSET $3
```

После шардирования этот запрос выполняет `GET /api/shards/users/{userId}/tasks`. Router вычисляет шард пользователя `gen_user_100` — Shard 2 — и запрос уходит только туда.

<!-- caption: Задачи пользователя gen_user_100 на каждом шарде (SQL на шардах) -->
| Шард | Задач пользователя |
|---|---|
| Shard 0 | 0 |
| Shard 1 | 0 |
| Shard 2 | 497 |

<!-- caption: План запроса на Shard 2 -->
```
Limit (actual time=0.020..0.025 rows=20 loops=1)
  Buffers: shared hit=5
  ->  Index Scan using idx_tasks_user_id_created_at on tasks (actual time=0.019..0.023 rows=20 loops=1)
        Index Cond: (user_id = '462b8287-da8e-4d42-9496-8c0a9653c776'::uuid)
Execution Time: 0.071 ms
```

**Почему запросу не нужны другие шарды.** Условие `WHERE user_id = $1` содержит shard key. Router — детерминированная функция от этого ключа, поэтому по `user_id` можно заранее сказать, где лежат все задачи пользователя: при записи каждая его задача попала на тот же шард. На других шардах этих строк нет по построению, и SQL на них это подтверждает — 0 строк. Запрос выполняется как на обычной базе: один сервер, один индекс, 5 буферов и 0.07 мс на шарде, 10–50 мс через API.

## 3. Агрегирующий запрос

**Запрос сервиса.** Статистика задач по статусам — `GET /api/tasks/stats`, метод `TaskRepository.GetStatusStatsAsync`:

<!-- caption: Агрегирующий запрос сервиса -->
```sql
SELECT status, count(*), count(*) FILTER (WHERE due_date < now() AND status IN (0, 1))
FROM tasks
GROUP BY status
```

После шардирования его выполняет `GET /api/shards/queries/stats`: запрос уходит на каждый шард, а сервис складывает ответы. Для среднего возраста задач шарды возвращают не средние, а сумму и количество, иначе объединение было бы неверным.

<!-- caption: Ответы шардов и результат объединения -->
| Шард | Задач | Строк в ответе шарда |
|---|---|---|
| Shard 0 | 339 959 | 4 (по одной на статус) |
| Shard 1 | 319 756 | 4 |
| Shard 2 | 340 285 | 4 |
| После объединения | **1 000 000** | 4 |

<!-- caption: Результат по статусам после объединения и проверка на основной базе -->
| Статус | count после объединения | count в основной базе | Средний возраст после объединения, дн. | В основной базе, дн. |
|---|---|---|---|---|
| Pending | 200 084 | 200 084 | 366.431 | 366.431 |
| InProgress | 199 766 | 199 766 | 367.454 | 367.454 |
| Completed | 550 260 | 550 260 | 367.059 | 367.059 |
| Cancelled | 49 890 | 49 890 | 368.670 | 368.670 |

Объединённый результат совпал с основной базой до единицы и до тысячной доли дня. COUNT на одном только Shard 0 дал 339 959 — треть правды.

<!-- caption: Время агрегации: шарды параллельно и по очереди (медиана 5 прогонов) -->
| Шардов | Параллельно, мс | По очереди, мс |
|---|---|---|
| 3 | 77 | 160 |
| 4 | 65 | 168 |

**1. Можно ли выполнить такой запрос только на одном shard?** Нет. В условии нет shard key, поэтому подходящие строки есть на каждом шарде, и любой один шард видит только свою часть данных. Запрос обязан уйти на все шарды — это scatter-gather.

**2. Где должны объединяться результаты?** В координаторе — в нашем случае в сервисе, в `DistributedTaskQueryService`. Базы шардов ничего не знают друг о друге и объединить результат не могут. Важно, что объединять можно не любые значения:
- `COUNT` и `SUM` складываются;
- `MIN` и `MAX` берутся по результатам шардов;
- `AVG` нельзя усреднять — шарды должны вернуть сумму и количество, а среднее считается уже после сложения. Тест `MergeStatuses_ShouldAddCountsAndComputeAverageFromTotals` показывает ошибку на простом примере: 10 задач по 10 дней на одном шарде и 90 задач по 1 дню на другом дают правильное среднее 1.9 дня, а «среднее средних» — 5.5. В реальных данных шарды похожи, и разница мала (366.431 против 366.410), но на неравномерных шардах она становится грубой ошибкой;
- `COUNT(DISTINCT …)` и медиану так просто не объединить: нужно собирать сами значения или приближённые структуры вроде HyperLogLog.

**3. Что происходит со временем выполнения при увеличении количества shard'ов?** Растёт число обращений: каждый шард — это отдельное подключение, запрос и ответ. При последовательном опросе время складывается из времени всех шардов: 3 шарда — 160 мс, 4 шарда — 168 мс, хотя данных на каждом стало меньше. При параллельном опросе время определяет самый медленный шард: на 4 шардах оно даже уменьшилось (77 → 65 мс), потому что каждый шард считает меньше строк. Но у параллельного варианта свои цены: нагрузка на все серверы одновременно, число соединений растёт с числом шардов, а хвост задержек равен задержке худшего шарда — чем шардов больше, тем вероятнее, что хотя бы один сейчас медленный.

## 4. JOIN между shard'ами

**Запрос сервиса.** Список задач для администратора — `TaskRepository.GetAllFilteredAsync`. EF Core строит JOIN четырёх таблиц:

<!-- caption: JOIN в запросе списка задач -->
```sql
SELECT t0.*, p.*, u.*, t1.*
FROM (SELECT t.* FROM tasks AS t WHERE … ORDER BY t.created_at DESC LIMIT $1 OFFSET $2) AS t0
LEFT JOIN projects AS p ON t0.project_id = p.id
INNER JOIN users AS u ON t0.user_id = u.id
LEFT JOIN (SELECT t2.task_id, t2.tag_id, t3.* FROM task_tags AS t2
           INNER JOIN tags AS t3 ON t2.tag_id = t3.id) AS t1
       ON t0.id = t1.task_id AND t0.created_at = t1.task_created_at
```

**Где находятся связанные данные.**

<!-- caption: Таблицы JOIN после шардирования -->
| Экземпляр | Таблицы |
|---|---|
| Shard 0, 1, 2 | `tasks` |
| Основная база | `users`, `projects`, `tags`, `task_tags` |

Тот же JOIN одним запросом на шарде невозможен:

<!-- caption: JOIN с проектами на шарде -->
```
ERROR:  relation "projects" does not exist
LINE 1: SELECT t.title, p.name FROM tasks t LEFT JOIN projects p ON ...
```

Поэтому в сервисе JOIN выполняется на стороне приложения (`GET /api/shards/queries/users/{id}/tasks-with-projects`):

<!-- caption: JOIN на стороне сервиса: задачи пользователя и названия проектов -->
| Шаг | Где | Запрос | Строк передано | Время |
|---|---|---|---|---|
| 1 | Shard 2 | задачи пользователя по `user_id`, 20 штук | 20 | 1.9 мс |
| 2 | основная база | `projects WHERE id = ANY(…)` по 14 собранным id | 14 | 15.4 мс |
| 3 | основная база | имя пользователя | 1 | 4.0 мс |
| 4 | сервис | соединение в памяти | — | — |
| Итого | | | 35 | 24.2 мс |

Для сравнения: этот же JOIN в одной базе выполняется одним запросом за 2.0 мс.

**1. Что произойдёт, если связанные записи находятся на разных shard'ах?** Обычный JOIN их не найдёт: каждый PostgreSQL соединяет только свои таблицы, и строки с другого сервера для него не существуют. Результат будет неполным или запрос вообще упадёт, как на шарде выше. Связывать данные приходится вне базы, за несколько запросов.

**2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?** Нет. Одним SQL-запросом можно соединять только таблицы одного сервера. Есть обходные механизмы — `postgres_fdw`, распределённые СУБД вроде Citus, — но это уже не обычный запрос: данные всё равно пересылаются между серверами, а планировщик плохо оценивает стоимость удалённых таблиц.

**3. Какие данные пришлось бы передавать между shard'ами?** Для application-side join: сначала строки одной стороны (20 задач), затем ключи соединения (14 `project_id`), затем найденные строки другой стороны (14 проектов). Для JOIN, у которого нет фильтра по shard key, — намного больше. Например, «все задачи проекта с именами исполнителей»: задачи проекта нужно собрать со всех шардов, так как все 1 000 проектов сервиса разбросаны по всем трём шардам. У самого большого проекта 277 задач на Shard 0, 293 на Shard 1 и 322 на Shard 2. Если бы и пользователи были шардированы по другому ключу, пришлось бы гонять между серверами целые промежуточные наборы строк.

**4. Можно ли выбрать shard key так, чтобы этот JOIN чаще выполнялся внутри одного shard?** Да, если связанные таблицы шардируются тем же ключом и лежат вместе (co-location):
- `task_tags` стоит хранить на шарде задачи: у связи тот же владелец, её можно положить по `user_id` задачи. Тогда соединение задач с тегами станет локальным;
- маленькие справочники — `tags`, `projects` — можно копировать на все шарды целиком (reference tables). Тогда JOIN с ними тоже выполняется на одном шарде, ценой синхронизации копий при изменениях;
- если бы главным запросом были «задачи проекта», подошёл бы shard key `project_id`. Но тогда распределёнными стали бы запросы «мои задачи», а у задачи без проекта не было бы ключа вовсе.

Shard key выбирается под самые частые JOIN и фильтры: для TaskManager это запросы пользователя, поэтому `user_id` остаётся правильным выбором, а справочники нужно копировать на шарды.

## 5. ORDER BY + LIMIT

**Запрос сервиса.** Первая страница списка задач администратора — новые задачи сверху:

<!-- caption: Запрос первой страницы новых задач -->
```sql
SELECT … FROM tasks ORDER BY created_at DESC LIMIT 10 OFFSET 0
```

После шардирования его выполняет `GET /api/shards/queries/newest`: каждый шард возвращает свои 10 самых новых задач, сервис сливает 30 строк в общий порядок и отдаёт первые 10.

<!-- caption: Первая страница после слияния: с какого шарда пришла каждая задача -->
| created_at | Шард | Задача |
|---|---|---|
| 2026-09-13 22:50:56 | Shard 2 | Task #839460 |
| 2026-09-13 22:50:34 | Shard 2 | Task #91296 |
| 2026-09-13 22:50:03 | Shard 1 | Task #497509 |
| 2026-09-13 22:49:05 | Shard 2 | Task #606862 |
| 2026-09-13 22:48:24 | Shard 1 | Task #203638 |
| 2026-09-13 22:47:40 | Shard 2 | Task #743702 |
| 2026-09-13 22:47:00 | Shard 2 | Task #165000 |
| 2026-09-13 22:46:56 | Shard 0 | Task #487095 |
| 2026-09-13 22:46:51 | Shard 0 | Task #394139 |
| 2026-09-13 22:45:51 | Shard 1 | Task #6891 |

Слитая страница совпала с тем же запросом к основной базе — те же 10 задач в том же порядке.

<!-- caption: Если взять первые 10 задач только с одного шарда -->
| Источник | Задач из настоящей первой страницы |
|---|---|
| только Shard 0 | 2 из 10 |
| только Shard 1 | 3 из 10 |
| только Shard 2 | 5 из 10 |

**Почему недостаточно получить первые 100 записей только с одного shard.** Каждый шард знает порядок только своих строк. Самые новые задачи системы распределены по шардам случайно — shard key `user_id` никак не связан со временем создания, — поэтому любой один шард содержит лишь часть глобальной первой страницы, а остальное вытеснили бы более новые строки других шардов. Правильный ответ требует взять с каждого шарда его top-N и слить их.

При этом с каждого шарда нужно брать не «свою страницу», а весь префикс до конца запрошенной страницы. Шард не знает, сколько строк новее его строк лежит на других шардах: в худшем случае вся страница может оказаться с одного шарда. Поэтому для страницы с номером P каждый шард отдаёт P × size строк:

<!-- caption: Глубокие страницы: сколько строк передаётся ради 10 строк ответа -->
| Страница | Строк с каждого шарда | Передано в сервис | Отдано клиенту | Время, мс |
|---|---|---|---|---|
| 1 | 10 | 30 | 10 | 23.5 |
| 10 | 100 | 300 | 10 | 25.1 |
| 100 | 1 000 | 3 000 | 10 | 29.8 |
| 1 000 | 10 000 | 30 000 | 10 | 87.8 |
| 5 000 | 50 000 | 150 000 | 10 | 178.7 |

Страница 100 после слияния тоже совпала с основной базой. Стоимость `OFFSET` в распределённой системе умножается на число шардов: ради 10 строк на странице 5 000 сервис получил 150 000 строк. Выход — keyset-пагинация: клиент передаёт `created_at` последней показанной задачи, и каждый шард отдаёт только 10 строк старше неё, на какой бы странице ни был пользователь.

## 6. Отказ одного shard

На работающем сервисе остановлен Shard 2 (`docker compose stop postgres-shard-2`). В сервисе к этому моменту уже была обработка: ошибка подключения к шарду превращается в ответ 503 с кодом `SHARD_UNAVAILABLE`, строка подключения содержит `Timeout=3`, чтобы не ждать 15 секунд по умолчанию. Опыт выявил ещё один случай — ошибку `57P01: terminating connection due to administrator command` на соединении, которое пул Npgsql открыл до остановки сервера. Она тоже теперь считается отказом шарда, а пул соединений к нему сбрасывается.

| `POST /api/auth/login` (основная база) | 200, 0.031 с | 200, 0.016 с |
| `GET /api/tasks` (реплика) | 200, 0.293 с | 200, 0.015 с |
| `GET /api/projects` (основная база) | 200, 0.106 с | 200, 0.010 с |
| Задачи `gen_user_2` (Shard 0) | 200, 0.030 с | **200**, 0.031 с |
| Задачи `gen_user_4` (Shard 2) | 200, 0.034 с | **503**, 1.292 с |
| Создание задачи `gen_user_4` (Shard 2) | 201, 1.513 с | **503**, 1.291 с |
| Статистика по всем шардам | 200, 0.123 с | **503**, 1.326 с |


После `docker compose start postgres-shard-2` сервис восстановился сам: задачи `gen_user_4` снова отдаются, статистика снова полная.

**1. Какие данные становятся недоступны?** Все задачи пользователей, которых router отправляет на Shard 2: 340 285 задач 3 390 пользователей — треть данных. Остальные задачи, а также пользователи, проекты и теги в основной базе остаются доступны.

**2. Какие endpoint'ы перестанут работать?**
- для пользователей Shard 2 — всё, что касается их задач: список, создание, изменение и удаление;
- для всех пользователей — распределённые запросы, которым нужны все шарды: общая статистика, общий список новых задач, поиск задачи по `id` без владельца.

Запросы пользователей Shard 0 и Shard 1 работают как раньше.

**3. Продолжит ли работать остальная часть сервиса?** Да. Вход в систему, проекты, теги, пользователи, health check и задачи двух других шардов ответили 200 с обычной скоростью. Шардирование изолировало отказ: пропала треть данных, а не весь сервис. При одной базе отказ сервера означал бы недоступность всего.

**4. Что должен делать backend при обращении к недоступному shard?**
- Быстро вернуть понятную ошибку, а не зависать: здесь это 503 `SHARD_UNAVAILABLE` за 1.3 секунды с номером шарда. 503 честно сообщает, что проблема временная и на стороне сервера, и клиент может повторить запрос позже.
- Не притворяться, что данных нет: пустой список задач вместо ошибки пользователь принял бы за потерю данных.
- Для распределённых запросов — дать выбор. По умолчанию 503, а при `allowPartial=true` — результат доступных шардов с явной пометкой `partial: true` и списком недоступных шардов. Для дашборда это приемлемо, для финансового отчёта — нет.
- Не записывать данные «куда-нибудь ещё»: создание задачи на другом шарде нарушило бы router, и задача потом не нашлась бы.
- Сбрасывать пул соединений к упавшему серверу, писать предупреждение в лог и отражать состояние шардов в health check.

**5. Как можно повысить отказоустойчивость?**
- У каждого шарда — реплика со streaming replication (ЛР № 4) и автоматическое переключение на неё при отказе (Patroni, pg_auto_failover).
- Чтение с реплики шарда, пока основной экземпляр недоступен.
- Circuit breaker в сервисе: после серии ошибок временно не ходить на упавший шард и сразу отвечать 503.
- Мониторинг и оповещение по каждому шарду (health check `/api/shards/queries/health` плюс alert, как в ЛР № 3).
- Регулярные резервные копии каждого шарда и отработанная процедура восстановления.
- Кэш для самых частых чтений: Redis уже используется для списков задач.

## 7. Hot Shard

Сервис выполняет 20 000 настоящих запросов «задачи пользователя» (`count` + страница из 20 задач на шарде пользователя). Меняется только то, какие пользователи делают запросы. Данные на шардах всё время одни и те же: 34.0 / 32.0 / 34.0 % задач.

<!-- caption: Распределение запросов по шардам при разном поведении пользователей -->
| Сценарий | Shard 0 | Shard 1 | Shard 2 |
|---|---|---|---|
| Доля задач на шарде | 34.00 % | 31.98 % | 34.03 % |
| Все пользователи одинаково активны | 35.16 % | 30.56 % | 34.27 % |
| Активность пропорциональна числу задач | 33.56 % | 32.70 % | 33.74 % |
| 50 % запросов — популярный `gen_user_1` (живёт на Shard 1) | 17.95 % | **65.02 %** | 17.03 % |
| 75 % запросов — `gen_user_1` | 8.95 % | **82.34 %** | 8.70 % |

<!-- caption: Нагрузка на шарды при 75 % запросов популярного пользователя -->
| Шард | Доля запросов | Доля строк | Строк прочитано | Среднее время, мс | p95, мс | Транзакций (pg_stat_database) |
|---|---|---|---|---|---|---|
| Shard 0 | 8.95 % | 34.00 % | 35 800 | 1.14 | 1.72 | 5 365 |
| Shard 1 | **82.34 %** | 31.98 % | 329 380 | **1.89** | **2.62** | **45 939** |
| Shard 2 | 8.70 % | 34.03 % | 34 820 | 1.13 | 1.74 | 5 232 |

Картина «10 % / 15 % / 75 %» из методички воспроизведена почти буквально: при одинаковом объёме данных Shard 1 получил 82 % запросов и в 8.6 раза больше транзакций, чем соседи, а его запросы стали медленнее на 66 %. Каждый запрос этого пользователя считает 9 900 его задач, а не сотню, как у обычного пользователя.

**Возможные причины hot shard.**
- **Неудачный shard key.** Если бы ключом был, например, `status`, большая часть задач (55 % — Completed) и почти все запросы попадали бы на один шард.
- **Неравномерное распределение данных.** Кольцо с малым числом виртуальных узлов дало одному из трёх шардов 39 % данных (ЛР № 5).
- **Популярный пользователь или tenant.** Главная причина в опыте: один ключ нельзя разделить, и вся его нагрузка ложится на один шард.
- **Определённый тип запросов.** Тяжёлые запросы — отчёты, экспорт, поиск без индекса — даже в небольшом количестве могут загрузить шард сильнее, чем тысячи лёгких запросов на соседних.

**Почему равное количество строк на shard'ах ещё не означает равномерную нагрузку.** Нагрузку создают запросы, а не строки. Количество строк описывает, как данные лежат, а нагрузка определяется тем, как часто и какими запросами к этим данным обращаются. Строки неравноценны: одни пользователи заходят раз в месяц, другие постоянно. Запросы тоже неравноценны: запрос тяжёлого пользователя читает в 100 раз больше строк. В опыте объём данных на шардах не изменился ни на строку, а доля запросов на Shard 1 выросла с 31 % до 82 %. Балансировать шарды нужно по фактической нагрузке — запросам, CPU, чтениям с диска, — а для этого её нужно измерять на каждом шарде.

## 8. Итоговый анализ shard key

**Подходит ли `user_id` для TaskManager? Да, с оговорками.** Сервис — это задачи пользователей, и почти все его операции выполняются от имени конкретного пользователя.

### Плюсы

<!-- caption: Запросы, которые shard key делает эффективными -->
| Операция | Почему эффективна |
|---|---|
| Список своих задач с фильтрами и сортировкой | один шард, индекс `(user_id, created_at)` — 0.07 мс на шарде |
| Создание, изменение, удаление своей задачи | один шард, транзакция в одной базе |
| Статистика своих задач | агрегация на одном шарде |
| Проверка владельца задачи | один шард, если известен `user_id` |
| Изоляция отказов | отказ шарда затрагивает только его пользователей |

Ключ не меняется, равномерно распределяет пользователей и позволяет добавлять шарды с переносом четверти данных (ЛР № 5).

### Минусы

<!-- caption: Запросы, которые становятся распределёнными -->
| Операция | Что происходит |
|---|---|
| Статистика и списки по всем задачам (администратор) | scatter-gather по всем шардам, объединение в сервисе |
| Задача по `id` без владельца | опрос всех шардов |
| Задачи проекта | все 1 000 проектов разбросаны по трём шардам |
| Задачи с проектами, пользователями и тегами | JOIN на стороне сервиса, несколько запросов к разным базам |
| Глубокая пагинация общего списка | каждый шард отдаёт весь префикс страницы |

### Проблемные операции

<!-- caption: Сложность операций после шардирования -->
| Операция | Сложность | Почему |
|---|---|---|
| JOIN | высокая | таблицы на разных серверах; только application-side join или копии справочников на шардах |
| Aggregation | средняя | scatter-gather; COUNT и SUM объединяются просто, AVG — через сумму и количество, DISTINCT и медиана — трудно |
| ORDER BY + LIMIT | средняя | слияние top-N; стоимость OFFSET умножается на число шардов |
| Migration | высокая | миграцию схемы нужно применить на каждом шарде; нет общей транзакции, шарды могут оказаться в разных версиях |
| Backup | средняя | копия каждого шарда отдельно; согласованный снимок всех шардов на один момент не получается сам |
| Восстановление | высокая | восстановленный шард отстаёт от остальных; ссылки между базами (задача → проект) могут указывать на данные из другого момента времени |
| Балансировка | высокая | горячий пользователь не делится между шардами; перенос данных нагружает шарды и требует окна, в котором router знает о переносе |

### Вывод

Если бы система проектировалась заново, shard key `user_id` стоило бы оставить. Он совпадает с тем, как сервисом пользуются: пользователь работает со своими задачами, и эти запросы — подавляющее большинство — выполняются на одном шарде так же быстро, как на отдельной базе. Альтернативы хуже. `project_id` делает распределёнными «мои задачи» и не подходит для задач без проекта. `id` задачи распределяет идеально, но превращает любой список в scatter-gather. `created_at` собирает всю свежую нагрузку на один шард.

Изменить стоило бы окружение ключа:
- таблицу `task_tags` хранить рядом с задачами на том же шарде;
- справочники `tags` и `projects` копировать на все шарды, чтобы основные JOIN стали локальными;
- административные отчёты по всем задачам перенести в отдельное аналитическое хранилище, куда данные шардов стекаются асинхронно, а не делать их scatter-gather к рабочим шардам;
- для очень крупных клиентов, если такие появятся, — выделенные шарды: горячий ключ при `user_id` неизбежен, и лучше заранее уметь выносить его отдельно.

## Вопросы для самопроверки

1. **Чем single-shard query отличается от distributed query?** Single-shard query содержит shard key, поэтому router заранее знает единственный шард, где лежат нужные строки, и запрос выполняется как на обычной базе: одно подключение, один план, локальные индексы. Distributed query ключа не содержит или требует данных нескольких шардов: его отправляют на все нужные шарды, а ответы объединяет координатор. Это дороже по сети и времени и зависит от доступности всех шардов. В работе список задач пользователя — single-shard (0.07 мс на шарде), общая статистика — distributed (77 мс, три шарда).

2. **Почему JOIN между shard'ами сложнее обычного JOIN?** Обычный JOIN выполняет одна база: планировщик видит обе таблицы, их статистику и индексы и выбирает способ соединения. Таблицы на разных серверах одним SQL-запросом не соединить. JOIN приходится выполнять в приложении за несколько обращений: получить строки одной стороны, собрать ключи, запросить по ним строки другой стороны и соединить в памяти. Данные передаются по сети, согласованность двух запросов не гарантирует общая транзакция, а удачный план приходится придумывать вручную.

3. **Как выполнить COUNT(\*) по всем shard'ам?** Отправить `COUNT(*)` на каждый шард — лучше параллельно — и сложить ответы в координаторе. Для группировок складываются значения с одинаковым ключом группы, для AVG шарды возвращают сумму и количество, а среднее считается после сложения. В работе: 339 959 + 319 756 + 340 285 = 1 000 000, что совпало с основной базой.

4. **Почему ORDER BY … LIMIT требует объединения результатов?** Первые N строк глобального порядка лежат на разных шардах, и никакой шард не знает, какие из его строк входят в общий top-N. Нужно взять top-N с каждого шарда, слить их в общий порядок и снова отрезать N. Первые 10 задач одного шарда содержали лишь 2, 3 или 5 задач настоящей первой страницы. Для страницы P каждый шард должен вернуть P × size строк, поэтому глубокие страницы дороги: 150 000 переданных строк ради 10 на странице 5 000.

5. **Что произойдёт при отказе одного shard?** Станут недоступны данные этого шарда — треть задач в опыте — и все запросы, которым нужны все шарды. Остальная часть сервиса продолжит работать: вход, проекты и задачи пользователей других шардов отвечали 200. Корректный сервис быстро возвращает понятную ошибку (503 `SHARD_UNAVAILABLE`), по явному запросу отдаёт неполный результат с пометкой и восстанавливается сам, когда шард возвращается.

6. **Что такое hot shard?** Шард, который получает непропорционально большую долю нагрузки и становится узким местом системы. В опыте Shard 1 при 32 % данных принял 82 % запросов и 45 939 транзакций против 5 365 у соседей, а его запросы стали на 66 % медленнее. Причины: популярный пользователь или tenant, неудачный shard key, неравномерное распределение данных или тяжёлые запросы к одному шарду.

7. **Почему выбор shard key влияет на JOIN?** JOIN выполняется локально, только если все соединяемые строки лежат на одном шарде. Это возможно, когда связанные таблицы шардированы тем же ключом (co-location) или скопированы на все шарды. При `user_id` задачи пользователя и связи этих задач с тегами можно положить вместе, и их JOIN станет локальным. А задачи одного проекта разбросаны по всем шардам — все 1 000 проектов в опыте, — поэтому любой JOIN «через проект» остаётся распределённым.

8. **Какие операции особенно плохо подходят для распределённых данных?**
   - JOIN между таблицами, шардированными разными ключами;
   - транзакции, меняющие данные на нескольких шардах;
   - глобальные ограничения уникальности и внешние ключи между базами;
   - глубокая пагинация через OFFSET;
   - `COUNT(DISTINCT)`, медианы и перцентили по всем данным;
   - согласованные резервные копии всех шардов и изменения схемы на всех шардах сразу.

9. **Что произойдёт при изменении количества shard'ов?** Часть ключей начнёт соответствовать другим шардам, и данные этих ключей нужно перенести до переключения router'а. При `hash % N` переносится большая часть данных — 75 % при переходе с трёх шардов на четыре. При consistent hashing — примерно доля нового шарда: 24–27 %, и только на новый шард (ЛР № 5). Пока идёт перенос, сервис должен знать, где сейчас данные переносимых пользователей, иначе чтение уйдёт на шард, где строк уже нет.

10. **Чем шардирование отличается от репликации?** Репликация копирует одни и те же данные целиком на несколько серверов. Она повышает отказоустойчивость и позволяет распределить чтение, но каждая копия хранит всё, а запись по-прежнему идёт на один Primary. Шардирование делит данные на части: каждый шард хранит только своё подмножество. Это масштабирует объём данных и запись, но каждая часть существует в одном экземпляре, и отказ шарда означает потерю доступа к его данным. На практике их совмещают: у каждого шарда есть свои реплики.

11. **Может ли шардирование сделать отдельный SQL-запрос быстрее?** Иногда да, но это не главная цель. Запрос по shard key работает с меньшей таблицей и меньшими индексами, которые лучше помещаются в память; агрегация параллельно на четырёх шардах в опыте оказалась быстрее, чем на трёх (65 против 77 мс). Однако запросы без shard key становятся медленнее и сложнее. Задача с проектами одним JOIN в одной базе — 2 мс, через шард и основную базу — 24 мс. Глубокая страница общего списка требует передачи сотен тысяч строк. Шардирование масштабирует объём данных и число одновременных операций, а скорость отдельного запроса обеспечивают индексы и хороший SQL.

## Заключение

В работе проанализированы реальные запросы сервиса TaskManager после шардирования задач по `user_id` на три PostgreSQL. Для каждого вида запроса поведение проверено на работающем сервисе: для этого добавлен сервис распределённых запросов с endpoint'ами `/api/shards/queries/…`.

Запрос задач пользователя остался single-shard: он выполняется индексом одного шарда за 0.07 мс, на других шардах этих строк нет. Агрегация по всем задачам стала scatter-gather: шарды возвращают свои части, сервис складывает их, и результат совпал с основной базой до единицы. AVG объединяется только через сумму и количество. Время при последовательном опросе растёт с числом шардов, а при параллельном определяется самым медленным шардом. JOIN задач с проектами одним SQL-запросом на шарде невозможен и выполняется в сервисе тремя запросами к двум базам: 24 мс вместо 2 мс в одной базе. ORDER BY + LIMIT требует слияния top-N со всех шардов: один шард содержал лишь 2–5 задач из настоящей первой десятки, а глубокие страницы стоят сотни тысяч переданных строк.

Отказ Shard 2 сделал недоступной треть задач и распределённые запросы, но не сервис целиком. Сервис отвечал 503 `SHARD_UNAVAILABLE` за 1.3 секунды, по запросу отдавал неполную статистику с пометкой и сам восстановился после возврата шарда. Опыт выявил и исправил ошибку обработки оборванных соединений из пула. Популярный пользователь, делающий 75 % запросов, превратил один шард в горячий — 82 % запросов при 32 % данных — и подтвердил, что равный объём данных не означает равную нагрузку.

Shard key `user_id` признан подходящим для сервиса: самые частые операции остаются локальными. Распределёнными становятся административные отчёты, запросы по проекту и JOIN со справочниками. Их стоит решать копированием справочников на шарды, хранением связей задач рядом с задачами и отдельным аналитическим хранилищем.
