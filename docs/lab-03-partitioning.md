## Часть 1. RANGE PARTITIONING по дате

Таблица `events` и три дневные партиции созданы по методичке в схеме `lab03`. В таблицу загружено 1 500 000 событий за 3 дня (2.5 s):

<!-- caption: Распределение событий по партициям -->
| Партиция | Границы | Строк |
|---|---|---|
| `events_2026_09_09` | `['2026-09-09', '2026-09-10')` | 499 953 |
| `events_2026_09_10` | `['2026-09-10', '2026-09-11')` | 499 429 |
| `events_2026_09_11` | `['2026-09-11', '2026-09-12')` | 500 618 |

Границы PostgreSQL хранит в каталоге (`pg_class.relpartbound`), их можно прочитать функцией `pg_get_expr`. Этим же запросом пользуется job из части 10:

```
  partition_name   |                               bounds
-------------------+--------------------------------------------------------------------
 events_2026_09_09 | FOR VALUES FROM ('2026-09-09 00:00:00') TO ('2026-09-10 00:00:00')
 events_2026_09_10 | FOR VALUES FROM ('2026-09-10 00:00:00') TO ('2026-09-11 00:00:00')
 events_2026_09_11 | FOR VALUES FROM ('2026-09-11 00:00:00') TO ('2026-09-12 00:00:00')
```

**Ответы на вопросы 1–4** (проверено вставкой граничных значений):

1. Запись с `created_at = '2026-09-10 12:00:00'` попала в `events_2026_09_10`: значение лежит внутри диапазона `['2026-09-10', '2026-09-11')`.
2. Запись с `created_at = '2026-09-11 00:00:00'` попала в `events_2026_09_11`: нижняя граница `FROM` включается в диапазон.
3. Запись за 2026-09-12 не вставилась: `ERROR: no partition of relation "events" found for row` (SQLSTATE 23514). Подходящей партиции нет, а DEFAULT-партиции тоже нет, поэтому PostgreSQL отказывает в `INSERT`. Для приложения это ошибка запроса и потерянные данные, поэтому партиции нужно создавать заранее (части 10–11).
4. Диапазон партиции полуоткрытый: `[FROM, TO)`. Верхняя граница не включается, чтобы соседние партиции стыковались без пересечений и без щелей: `TO` одной партиции равно `FROM` следующей. Если бы граница включалась, значение `2026-09-11 00:00:00` принадлежало бы двум партициям. Писать «до конца дня» как `'2026-09-10 23:59:59.999999'` тоже плохо: такая граница зависит от точности типа и легко оставляет щель.

## Часть 2. Partition pruning

### Запрос с условием по ключу партиционирования

<!-- caption: План запроса за 10 сентября -->
```
Finalize Aggregate (actual time=29.283..32.616 rows=1 loops=1)
  Buffers: shared hit=4726
  ->  Gather (actual time=29.083..32.606 rows=3 loops=1)
        Workers Launched: 2
        ->  Partial Aggregate (actual time=26.217..26.218 rows=1 loops=3)
              ->  Parallel Seq Scan on events_2026_09_10 events (actual rows=166477 loops=3)
                    Filter: ((created_at >= '2026-09-10 00:00:00') AND (created_at < '2026-09-11 00:00:00'))
Planning Time: 0.075 ms
Execution Time: 32.703 ms
```

- **Сколько партиций проверил PostgreSQL.** Планировщик сравнил условие с границами всех трёх партиций, но в план попала только одна. Остальные две не читались совсем.
- **Какая партиция нужна.** `events_2026_09_10`: все строки за 10 сентября лежат в ней.
- **Удалось ли исключить остальные.** Да. В плане нет узла `Append` над несколькими партициями, прочитано 4 726 буферов, это ровно одна партиция.
- **Где в плане видно pruning.** В самом составе плана: сканируется одна партиция `events_2026_09_10` вместо трёх. Это отсечение при планировании: границы запроса — константы. Если граница вычисляется при выполнении (`now()`), отсечение происходит на старте исполнения, и в плане появляется строка `Subplans Removed: 1`:

<!-- caption: Отсечение при выполнении: граница вычисляется от now() -->
```
->  Parallel Append (actual time=0.012..68.215 rows=187938 loops=3)
      Subplans Removed: 1
      ->  Parallel Seq Scan on events_2026_09_11 events_2 ...
      ->  Parallel Seq Scan on events_2026_09_10 events_1 ...
            Filter: (created_at >= ((now())::timestamp without time zone - '1 day'::interval))
```

Для сравнения тот же запрос выполнен на обычной таблице `events_flat` с теми же 1.5 млн строк:

<!-- caption: Запрос за сутки: партиции против обычной таблицы -->
| Вариант | Партиций в плане | Прочитано буферов | Rows Removed by Filter | Время |
|---|---|---|---|---|
| Партиции по дням | 1 из 3 | 4 726 | 0 | 32.7 ms |
| Обычная таблица | — | 14 208 | 1 000 572 | 50.2 ms |

Таблица без партиций читает все 1.5 млн строк и отбрасывает две трети фильтром. Партиционированная таблица читает только нужную треть.

### Запрос без ключа партиционирования

<!-- caption: План запроса event_type = 'click' -->
```
Finalize Aggregate (actual time=37.997..42.032 rows=1 loops=1)
  Buffers: shared hit=14195
  ->  Parallel Append (actual time=0.020..33.570 rows=10012 loops=3)
        ->  Parallel Seq Scan on events_2026_09_11 events_3
              Filter: ((event_type)::text = 'click'::text)
              Rows Removed by Filter: 163584
        ->  Parallel Seq Scan on events_2026_09_09 events_1
              Rows Removed by Filter: 244980
        ->  Parallel Seq Scan on events_2026_09_10 events_2
              Rows Removed by Filter: 489256
Planning Time: 0.098 ms
Execution Time: 42.090 ms
```

**Почему второй запрос обращается ко всем партициям.** Условие `event_type = 'click'` не содержит ключа партиционирования `created_at`. Партиции разделены только по дате, поэтому PostgreSQL не знает, в каких из них есть клики: клик мог произойти в любой день. Отсечь нечего, и узел `Append` читает все три партиции (14 195 буферов, 1.47 млн строк отброшено фильтром).

## Часть 3. RANGE PARTITIONING по числовому значению

Таблица `products` разбита по цене на `products_cheap` `[0, 100)`, `products_medium` `[100, 1000)` и `products_expensive` `[1000, MAXVALUE)`. Граничные цены легли так:

<!-- caption: Граничные значения цены -->
| Товар | Цена | Партиция |
|---|---|---|
| Карандаш | 15 | `products_cheap` |
| Тетрадь | 99.99 | `products_cheap` |
| Рюкзак | 100 | `products_medium` |
| Наушники | 999.99 | `products_medium` |
| Монитор | 1000 | `products_expensive` |
| Ноутбук | 85 000 | `products_expensive` |

После загрузки 300 000 товаров с ценой от 1 до 5 000: cheap — 5 924, medium — 53 948, expensive — 240 134. Товар с отрицательной ценой не вставился (`no partition of relation "products" found for row`): нижняя граница первой партиции — 0.

**Какие партиции нужно просмотреть для `price >= 100 AND price < 500` и почему.** Только `products_medium`: диапазон `[100, 500)` целиком внутри её границ `[100, 1000)` и не пересекается с остальными. План это подтверждает — один `Seq Scan on products_medium`, 448 буферов, 7.3 ms. Если диапазон задевает две партиции, например `price >= 50 AND price < 150`, в плане появляются обе: `Append` над `products_cheap` и `products_medium`.

## Часть 4. LIST PARTITIONING

Клиенты разбиты по типу: `customers_b2c` (209 933), `customers_b2b` (75 001), `customers_enterprise` (15 066).

<!-- caption: План запроса customer_type = 'B2B' -->
```
Seq Scan on customers_b2b customers (actual time=0.011..9.403 rows=75001 loops=1)
  Filter: ((customer_type)::text = 'B2B'::text)
  Buffers: shared hit=601
Planning Time: 0.138 ms
Execution Time: 12.543 ms
```

- **Какая партиция используется.** Только `customers_b2b`.
- **Почему PostgreSQL не обращается к другим.** Каждая партиция принимает только значения из своего списка `FOR VALUES IN (...)`. Планировщик сравнивает константу `'B2B'` со списками и знает, что в `customers_b2c` и `customers_enterprise` таких строк быть не может. Фильтр в плане ничего не отбрасывает: в партиции все строки — B2B.
- **Отличие от RANGE.** RANGE делит упорядоченное множество значений на интервалы, и отсечение работает для сравнений `<`, `>`, `BETWEEN`. LIST перечисляет конкретные значения без порядка: отсечение работает для `=` и `IN` (запрос `IN ('B2B', 'Enterprise')` читает две партиции). Новое значение, которого нет ни в одном списке, требует новой партиции или DEFAULT.

## Часть 5. LIST PARTITIONING: неизвестное значение

Вставка клиента с типом `VIP` без DEFAULT-партиции завершилась ошибкой `no partition of relation "customers" found for row`. После `CREATE TABLE customers_default PARTITION OF customers DEFAULT` та же вставка прошла, строка оказалась в `customers_default`.

**Ответы:**

1. **Зачем нужна DEFAULT partition.** В неё попадают строки, значение ключа которых не подходит ни одной другой партиции. Без неё такая вставка завершается ошибкой.
2. **Чем она полезна.** Это страховка от неожиданных данных: появился новый тип клиента — приложение продолжает работать, данные не теряются, партицию для нового значения можно создать позже.
3. **Какие проблемы возникают, если постоянно складывать новые значения в DEFAULT.** В эксперименте проявились все три:
   - **Нельзя создать партицию для значения, которое уже лежит в DEFAULT.** `CREATE TABLE customers_vip PARTITION OF customers FOR VALUES IN ('VIP')` упал с ошибкой `updated partition constraint for default partition "customers_default" would be violated by some row`. Пришлось в одной транзакции отсоединить DEFAULT, создать партицию, перенести строки и присоединить DEFAULT обратно.
   - **DEFAULT читается запросами по любому значению не из списков.** Запрос `customer_type = 'Premium'` сканирует `customers_default`. Когда в DEFAULT копятся разные значения, она превращается в обычную большую неразделённую таблицу, и пользы от партиционирования для этих значений нет.
   - **DEFAULT скрывает проблему.** Ошибки нет, поэтому никто не узнаёт, что данные лежат не там. При создании каждой новой партиции PostgreSQL сканирует DEFAULT под блокировкой, чтобы проверить, что в ней нет строк для нового значения, — чем она больше, тем дольше блокировка.

   По этой же причине в таблице `tasks` (часть 12) DEFAULT-партиции нет: отсутствие будущей партиции должно обнаруживаться проверкой, а не маскироваться.

## Часть 6. HASH PARTITIONING

В `user_events` с 4 HASH-партициями по `user_id` загружен 1 000 000 событий 100 000 пользователей за 3 года:

<!-- caption: Распределение по HASH-партициям -->
| Партиция | Строк | Доля | Пользователей |
|---|---|---|---|
| `user_events_0` | 251 508 | 25.15% | 25 124 |
| `user_events_1` | 250 013 | 25.00% | 24 977 |
| `user_events_2` | 249 226 | 24.92% | 24 970 |
| `user_events_3` | 249 253 | 24.93% | 24 924 |

**Ответы:**

1. **Насколько равномерно распределились данные.** Почти идеально: отклонение от 25% не больше 0.15 процентного пункта. Равномерность держится, пока пользователей много и ни один не даёт заметную долю строк.
2. **Чем полезен HASH.** Он делит большую таблицу на части одинакового размера, когда естественных диапазонов или категорий нет. Каждая партиция и её индексы меньше, `VACUUM` и `ANALYZE` идут по частям. Запрос по конкретному пользователю читает одну партицию: `user_id = 42` — только `user_events_2`.
3. **Чем HASH отличается от RANGE.** RANGE кладёт рядом соседние значения ключа, поэтому отсекает партиции для диапазонов и позволяет удалять старые данные целыми партициями. HASH раскладывает значения по остатку от хэша: отсечение работает только для равенства, а соседние значения оказываются в разных партициях. Число HASH-партиций задаётся модулем при создании, и поменять его без перезаписи данных нельзя.
4. **Почему HASH плохо подходит для «удалить данные старше 3 лет».** Старые события равномерно размазаны по всем партициям. Запрос за период читает все 4 партиции, а удаление превращается в `DELETE` по всем партициям: здесь 27 713 строк за 57 ms, а на миллиардах строк это часы, огромный объём WAL и раздувание таблиц до следующего `VACUUM`. В RANGE по дате те же данные удаляются мгновенно: `DETACH` и `DROP` старой партиции.

## Часть 7. Выбор стратегии партиционирования

<!-- caption: Выбор стратегии для сценариев -->
| Сценарий | Стратегия и ключ | Обоснование |
|---|---|---|
| A. Миллионы событий в день, удаление данных старше 3 лет | RANGE по `created_at`, партиция на день или месяц | Старые данные удаляются `DROP`/`DETACH` целой партиции мгновенно и без раздувания. Запросы за период читают только свои партиции |
| B. Три типа пользователей, запросы фильтруют по типу | LIST по `customer_type` | Значений мало, они известны заранее и не упорядочены. Запрос с `=` читает одну партицию |
| C. Равномерно распределить по `user_id` | HASH по `user_id` | Естественных диапазонов нет, HASH даёт партиции одинакового размера, запрос по пользователю читает одну партицию |
| D. Заказы, аналитика по `created_at BETWEEN …` | RANGE по `created_at` | Диапазон по ключу отсекает все партиции вне периода. Каждая партиция — законченный период |
| E. Платежи по странам EE, LV, LT, FI, SE | LIST по коду страны | Набор стран дискретный и заранее известен. Мелкие страны можно объединить в одну партицию: `FOR VALUES IN ('EE', 'LV', 'LT')`. DEFAULT — только вместе с контролем её размера |

## Часть 8. Партиционирование и индексы

Индекс `idx_events_user_id` создан на родительской таблице, PostgreSQL сам создал по индексу в каждой партиции:

<!-- caption: Индексы партиций -->
| Индекс | Размер |
|---|---|
| `events_2026_09_09_user_id_idx` | 5 784 kB |
| `events_2026_09_10_user_id_idx` | 5 776 kB |
| `events_2026_09_11_user_id_idx` | 5 784 kB |

<!-- caption: План запроса за сутки по user_id -->
```
Bitmap Heap Scan on events_2026_09_10 events (actual time=0.018..0.021 rows=5 loops=1)
  Recheck Cond: (user_id = 12345)
  Filter: ((created_at >= '2026-09-10 00:00:00') AND (created_at < '2026-09-11 00:00:00'))
  Buffers: shared hit=8
  ->  Bitmap Index Scan on events_2026_09_10_user_id_idx (actual rows=5 loops=1)
        Index Cond: (user_id = 12345)
Planning Time: 0.050 ms
Execution Time: 0.057 ms
```

1. **Какие партиции отфильтрованы.** `events_2026_09_09` и `events_2026_09_11`. В плане только `events_2026_09_10`.
2. **Используется ли индекс.** Да: `Bitmap Index Scan on events_2026_09_10_user_id_idx`, прочитано 8 буферов вместо 4 726 при полном чтении партиции.
3. **На каком уровне существует индекс.** Индекс на родителе — партиционированный: он не хранит данных, а описывает, что у каждой партиции должен быть такой индекс. Реальные B-tree — локальные индексы партиций, по одному на партицию. Новые партиции получают индекс автоматически, в том числе партиции, которые создаёт job. Глобального индекса по всей таблице в PostgreSQL нет.
4. **Почему комбинация эффективнее одного механизма.**

<!-- caption: Поиск по user_id: партиции, индекс и их комбинация -->
| Вариант | Что читается | Буферов | Время |
|---|---|---|---|
| Сутки + `user_id`, партиции + индекс | 1 индекс, 1 партиция | 8 | 0.057 ms |
| Только `user_id`, партиции + индекс | 3 индекса, 3 партиции | 25 | 0.117 ms |
| Сутки + `user_id`, обычная таблица + индекс | 1 большой индекс, 16 строк за 3 дня, 11 отброшено | 19 | 0.049 ms |
| Сутки, партиции без индекса (часть 2) | вся партиция | 4 726 | 32.7 ms |

Партиционирование отвечает на вопрос «в какой части данных искать», индекс — «как найти строки внутри этой части». Одно отсечение без индекса всё равно читает целую партицию (500 тыс. строк). Индекс без партиций работает, но растёт вместе со всей таблицей и возвращает строки за все дни, которые потом отбрасываются фильтром (11 из 16). Вместе они читают маленький индекс одной партиции и только нужные строки. На 1.5 млн строк разница в микросекундах. На сотнях миллионов строк индекс одной партиции помещается в память, а общий — нет.

## Часть 9. Когда партиционирование не помогает

<!-- caption: Запрос по event_type с индексом и без -->
| Вариант | Партиций | Сканирование | Буферов | Rows Removed | Время |
|---|---|---|---|---|---|
| Партиции, без индекса | 3 из 3 | Parallel Seq Scan | 14 195 | 1 469 968 | 41.6 ms |
| Партиции + `idx_events_event_type` | 3 из 3 | Index Only Scan | 38 | 0 | 7.4 ms |
| То же + условие на сутки | 1 из 3 | Bitmap Heap Scan | 4 185 | 0 | 6.6 ms |

**Почему партиционирование само по себе не решило проблему.** Условие не содержит ключа `created_at`, поэтому отсечения нет, и запрос читает все партиции целиком — столько же данных, сколько обычная таблица. Партиционирование уменьшает объём чтения только для запросов по ключу. Для фильтра по другой колонке нужен индекс: он превратил полное чтение 1.5 млн строк в чтение 38 страниц индекса.

**Вывод.** Партиционирование отвечает на одну проблему — объём данных, который нужно просмотреть для запроса по ключу, и стоимость обслуживания большой таблицы. Индекс отвечает на другую — быстрый поиск строк по условию.

## Часть 10. Автоматическое создание партиций

Задача создания партиций реализована в сервисе TaskManager и обслуживает две таблицы: учебную `lab03.events` (партиция на день) и таблицу сервиса `tasks` (партиция на месяц, часть 12). Таблицы и горизонт задаются в конфигурации:

<!-- caption: Настройки задачи в appsettings.json -->
```
"Partitioning": {
  "Enabled": true,
  "JobTimeUtc": "01:00:00",
  "CheckInterval": "00:05:00",
  "Tables": [
    { "Table": "tasks", "Interval": "Month", "PeriodsAhead": 3 },
    { "Table": "lab03.events", "Interval": "Day", "PeriodsAhead": 3, "RetentionPeriods": 30 }
  ]
}
```

<!-- caption: Компоненты задачи -->
| Компонент | Слой | Что делает |
|---|---|---|
| `PartitionPlanner` | Application | Чистые вычисления: начало периода, имя партиции (`events_2026_09_14`, `tasks_2026_09`), список требуемых партиций, отсутствующие, устаревшие |
| `PartitionRepository` | Infrastructure (Dapper) | Читает партиции из каталога (`pg_inherits` + `pg_get_expr(relpartbound)`), создаёт `CREATE TABLE IF NOT EXISTS … PARTITION OF … FOR VALUES FROM … TO …`, удаляет `DETACH` + `DROP` |
| `PartitionMaintenanceService.EnsurePartitionsAsync` | Application | Сам CreatePartitionsJob |
| `PartitionMaintenanceWorker` | API (`BackgroundService`) | Запускает job при старте сервиса и каждую ночь в 01:00 UTC |
| `POST /api/partitions/ensure` | API, роль Admin | Ручной запуск job |

Шаги job повторяют схему из методички: определить сегодняшнюю дату (UTC) → определить горизонт (текущий период и 3 вперёд) → получить существующие партиции → найти отсутствующие → создать их. Требования выполнены так:

<!-- caption: Требования к job -->
| Требование | Как выполнено |
|---|---|
| Создавать недостающие партиции | Для каждого требуемого диапазона ищется партиция, которая его покрывает. Для каждого непокрытого выполняется `CREATE TABLE … PARTITION OF` |
| Не создавать уже существующие | Наличие определяется по границам из каталога, а не по имени: партиция с другим именем, но с нужным диапазоном, тоже считается. Вторая защита — `CREATE TABLE IF NOT EXISTS` |
| Безопасна при повторном запуске | Повторный запуск находит 0 отсутствующих и ничего не создаёт (тест `EnsurePartitionsAsync_ShouldBeIdempotent`) |
| Логировать результат | Каждый запуск пишет в лог сервиса число существующих, требуемых и отсутствующих партиций и каждую созданную |

Первый запуск после развёртывания (сегодня по UTC — 2026-09-11, у `lab03.events` были только три партиции из части 1):

<!-- caption: Лог первого запуска job -->
```
[21:18:16 INF] Partition job started at 2026-09-11 21:18:16 UTC
[21:18:16 INF] Table tasks: existing partitions 29, required 4, missing 0
[21:18:16 INF] Table lab03.events: existing partitions 3, required 4, missing 3
[21:18:16 INF] Creating partition events_2026_09_12
[21:18:16 INF] Partition events_2026_09_12 created successfully
[21:18:16 INF] Creating partition events_2026_09_13
[21:18:16 INF] Partition events_2026_09_13 created successfully
[21:18:16 INF] Creating partition events_2026_09_14
[21:18:16 INF] Partition events_2026_09_14 created successfully
[21:18:16 INF] Partition job finished with status Ok
```

**Запас в один период.** Горизонт сдвигается в полночь, а job запускается в 01:00. Если создавать партиции ровно на 3 дня вперёд, то с 00:00 до 01:00 проверка из части 11 видела бы, что партиции «сегодня + 3» нет, и отправляла бы ложный alert. Поэтому job создаёт на один период больше, чем требует проверка: 4 дня вперёд для `events` и 4 месяца для `tasks` (тест `CheckAsync_ShouldStayOk_AfterMidnightBeforeNightlyJob`). После этого изменения перезапуск сервиса досоздал по одной партиции:

<!-- caption: Лог запуска job с запасом -->
```
[21:22:55 INF] Table tasks: existing partitions 29, required 5, missing 1
[21:22:55 INF] Creating partition tasks_2027_01
[21:22:55 INF] Partition tasks_2027_01 created successfully
[21:22:55 INF] Table lab03.events: existing partitions 6, required 5, missing 1
[21:22:55 INF] Creating partition events_2026_09_15
[21:22:55 INF] Partition events_2026_09_15 created successfully
```

**Удаление старых партиций.** Для `lab03.events` задано хранение 30 дней (`RetentionPeriods`): job отсоединяет и удаляет партиции, которые целиком старше границы, — это `DROP` таблицы, а не `DELETE` строк (часть 6). Для `tasks` хранение не задано: задачи — рабочие данные пользователей, их нельзя удалять по возрасту.

Логика покрыта модульными тестами: планировщик, разбор границ из `pg_get_expr`, политика алертов и сервис целиком на подменённых часах (`TimeProvider`) и хранилище в памяти. Всего в проекте 93 теста, все проходят.

## Часть 11. Production-сценарий: ночной job сломался

### Проверка PartitionHealthCheck

Проверка — метод `PartitionMaintenanceService.CheckAsync`. Он строит тот же список требуемых партиций, что и job, но без запаса: текущий период и 3 вперёд. Если какой-то нет, результат — CRITICAL:

<!-- caption: Результат проверки при пропавшей партиции -->
| Дата | Партиция | Есть |
|---|---|---|
| 11 сентября | `events_2026_09_11` | ✓ |
| 12 сентября | `events_2026_09_12` | ✓ |
| 13 сентября | `events_2026_09_13` | ✓ |
| 14 сентября | `events_2026_09_14` | ✗ → **CRITICAL** |

Проверка доступна тремя способами:

- `PartitionMaintenanceWorker` запускает её каждые 5 минут (`CheckInterval`) и отправляет уведомления;
- `POST /api/partitions/check` — ручной запуск с уведомлениями, `GET /api/partitions` — состояние без уведомлений (роль Admin);
- `GET /health/partitions` — стандартный health check ASP.NET Core для систем мониторинга: `200 Healthy` или `503 Unhealthy` со списком отсутствующих партиций. Общий `/health` эту проверку не включает: пропавшая будущая партиция не делает весь сервис «нерабочим».

### Отправка уведомления (задание 11.1)

Канал — Telegram-бот (Bot API, метод `sendMessage`), класс `TelegramAlertNotifier`. Токен бота и chat id берутся из локального файла `.env`: он указан в `.gitignore` и не попадает в репозиторий (шаблон — `.env.example`). Docker Compose передаёт их в контейнер API переменными окружения. Токен входит в URL запроса к Telegram, поэтому для этого `HttpClient` отключено логирование запросов, иначе токен попал бы в лог. Без токена сообщение пишется только в лог.

### Один alert вместо бесконечных повторов (задание 11.4)

Состояние последней проверки хранится в таблице `partition_alert_state` (миграция 013): статус, список отсутствующих партиций, время изменения и время доставленного уведомления. Решение принимает `AlertPolicy`: уведомление отправляется только при смене состояния.

<!-- caption: Правила отправки уведомлений -->
| Предыдущая проверка | Текущая | Действие |
|---|---|---|
| нет или OK | CRITICAL | отправить alert |
| CRITICAL, alert доставлен, тот же список | CRITICAL | ничего |
| CRITICAL, alert доставлен, список изменился | CRITICAL | отправить alert: это новая проблема |
| CRITICAL, alert не доставлен | CRITICAL | повторить отправку |
| CRITICAL, alert доставлен | OK | отправить recovery |
| нет или OK | OK | ничего |

<!-- caption: Хронология демонстрации -->
| Время (UTC) | Состояние | Действие |
|---|---|---|
| 21:23:30 | CRITICAL | alert отправлен |
| 21:23:32 | CRITICAL | `already notified` — не отправлять повторно |
| 21:23:33 | — | job создал `events_2026_09_14` |
| 21:23:34 | OK | recovery отправлен |

Сценарий из методички (08:00 CRITICAL → alert, 08:05 и 08:10 — тишина, 08:15 OK → recovery) проверяется тестом `CheckAsync_ShouldAlertOnceAndSendRecovery` на подменённых часах. Состояние хранится в базе, а не в памяти процесса: после перезапуска сервиса старая проблема не порождает новый alert. Если Telegram недоступен, состояние сохраняется без отметки о доставке, и следующая проверка отправляет alert снова (тест `CheckAsync_ShouldRetryAlertThatWasNotDelivered`).

Ограничение решения: проверку выполняет тот же сервис, что и job. Если сервис лежит целиком, молчат оба, поэтому `/health/partitions` стоит опрашивать внешним мониторингом (Prometheus, Uptime Kuma и т. п.).

## Часть 12. Партиционирование собственной базы данных

### Шаги 1–4. Таблица, ключ, стратегия и обоснование

<!-- caption: Решение для сервиса TaskManager -->
| Шаг | Решение |
|---|---|
| Таблица | `tasks` |
| Ключ | `created_at` |
| Стратегия | RANGE, партиция на календарный месяц (`tasks_2026_09`), без DEFAULT-партиции |
| Горизонт | текущий месяц + 3 вперёд (job создаёт + 4) |

**Почему `tasks`.** Это самая большая таблица сервиса: 5 000 001 строка, 1.5 GB с индексами, и она растёт быстрее остальных — около 208 тысяч задач в месяц. Остальные таблицы маленькие (пользователи, проекты, теги). Связи `task_tags` — производная таблица: они живут и удаляются вместе с задачей.

**Почему `created_at`.** Ключ удовлетворяет всем требованиям из контрольного вопроса 7:
- он есть в самых частых запросах: список задач по умолчанию сортируется по `created_at DESC`, а в API добавлен фильтр по периоду создания `createdFrom`/`createdTo`;
- он не меняется: `UpdateAsync` не трогает `CreatedAt`, поэтому строка никогда не переезжает между партициями;
- он всегда заполнен (`NOT NULL DEFAULT now()`) и даёт партиции одинакового размера;
- он совпадает с жизненным циклом данных: новые задачи читают и меняют чаще старых.

Другие варианты отклонены. HASH по `user_id` не помогает запросам за период и архивированию, а запросы по пользователю уже обслуживает индекс `(user_id, created_at)`. LIST по `status` — ключ меняется (задача переходит Pending → Completed и переезжает в другую партицию), а значений всего 4 с перекосом: Completed — 55 %. `project_id` может быть `NULL`, и значений много.

**Почему RANGE по месяцу.** RANGE — естественная стратегия для времени: запрос за период читает только свои партиции. Размер партиции выбран по измерениям:

<!-- caption: Цена числа партиций: 1 млн строк, запрос без ключа -->
| Партиций | Planning Time | Execution Time | Запрос по ключу |
|---|---|---|---|
| 10 | 0.139 ms | 32.1 ms | 3.9 ms |
| 100 | 0.642 ms | 36.1 ms | 0.36 ms |
| 1 000 | 12.053 ms | 97.2 ms | 0.047 ms |

Чем больше партиций, тем быстрее запросы по ключу, но тем дороже все остальные: у запроса без ключа время планирования выросло в 87 раз, а выполнения — в 3 раза. При партиции на день у `tasks` было бы около 750 партиций по 7 тысяч строк, и запросы по `id` и статистика платили бы эту цену. Партиция на год слишком крупная: отчёт за месяц читал бы 2.5 млн строк. Месяц даёт 12 партиций в год по ~208 тысяч строк (~50 MB).

**DEFAULT-партиции нет.** Задачи создаются «сейчас», поэтому ключ всегда попадает в текущий месяц. Если партиции нет, это сбой job, и его должна обнаружить проверка, а не скрыть DEFAULT (часть 5).

**Какие запросы должны получить пользу.** Списки задач за период `GET /api/tasks?createdFrom=…&createdTo=…` для администратора и пользователя, в том числе с фильтром по статусу, и первая страница без фильтров. Не получат пользы запросы без ключа: задача по `id` и статистика по всем задачам.

### Миграция таблицы

Партиционирование выполнено миграцией Liquibase `012-partition-tasks-by-created-at.xml`. Существующую таблицу нельзя сделать партиционированной командой `ALTER`, поэтому миграция:
1. переименовывает `tasks` в `tasks_unpartitioned` и создаёт новую `tasks … PARTITION BY RANGE (created_at)`;
2. создаёт партиции от самого раннего месяца с данными до текущего месяца + 3;
3. переносит строки (`INSERT … SELECT`) и удаляет старую таблицу;
4. создаёт первичный ключ, внешние ключи и 6 индексов на родителе — PostgreSQL создаёт их копии в каждой партиции;
5. `ANALYZE`; блок `rollback` возвращает обычную таблицу.

На 5 млн задач и 4 млн связей миграция заняла около 3 минут. Два ограничения PostgreSQL потребовали изменений в коде:

<!-- caption: Ограничения PostgreSQL и изменения в сервисе -->
| Ограничение | Изменение |
|---|---|
| Первичный и уникальные ключи партиционированной таблицы обязаны включать ключ партиционирования | `tasks_pkey` = `(id, created_at)`. Уникальность одного `id` теперь обеспечивает приложение: `Guid.NewGuid()` |
| Внешний ключ может ссылаться только на уникальный ключ целиком | В `task_tags` добавлена колонка `task_created_at`, внешний ключ `(task_id, task_created_at) → tasks (id, created_at)`. В EF Core — `HasPrincipalKey(t => new { t.Id, t.CreatedAt })`, вставка через Dapper берёт `created_at` из `tasks` |

### Шаг 5. Партиции

Миграция создала 29 партиций (`tasks_2024_08` … `tasks_2026_12`), job досоздал `tasks_2027_01`. Строки распределились равномерно: полный месяц — 207 735 … 208 918 задач, первый месяц — 139 655, текущий — 68 502 (месяц не закончился), будущие пусты. Размер таблицы с индексами уменьшился с 1 502 MB до 1 414 MB: таблица переписана заново, без «мёртвых» строк от прошлых экспериментов.

**Разбор результатов.**
- **Q3/A2 ускорился в 78 раз.** До партиционирования PostgreSQL объединял два индекса (`BitmapAnd`): диапазон дат дал 48 557 строк, а `status = 0` — 1 000 904 строки. Только построение битовой карты по статусу заняло 200 ms, затем читались 20 007 страниц, разбросанных по всей таблице. После партиционирования запрос работает внутри `tasks_2026_09`: там 68 502 строки, индекс по статусу даёт 13 853, и читается 1 217 страниц одной небольшой партиции.
- **Q1 почти не изменился по времени.** На обычной таблице это Index Only Scan по диапазону индекса (137 тысяч обращений к карте видимости), на партиционированной — полное чтение одной партиции: 3 655 страниц. Оба способа читают только нужный месяц. При повторном запуске через API получилось 17 ms.
- **Страницы списков (Q2, Q4, Q5, A1, A3) и так брали 10 строк из индекса за доли миллисекунды.** Партиционирование их не ухудшило, время планирования выросло на десятые доли миллисекунды.
- **Q6/A6 — не отсечение, а упорядоченный `Append`.** Партиции идут в порядке `created_at`, поэтому PostgreSQL читает их с самой новой. Первые 10 строк нашлись в `tasks_2026_09`, остальные 25 партиций помечены `never executed`.
- **Запросы без ключа стали дороже.** `GET /api/tasks/{id}` проверяет индекс первичного ключа каждой партиции, пока не найдёт строку: 26 проверок вместо одной, 0.02 → 0.56 ms. Это всё ещё меньше миллисекунды, но время растёт с числом партиций. Если передавать в API и `created_at`, запрос уйдёт в одну партицию. Статистика по всем задачам читает всё и стала медленнее на 45 % из-за накладных расходов `Append` над 30 партициями. Такой запрос нужно кэшировать или считать заранее (материализованное представление из ЛР № 2).

## Ответы на контрольные вопросы

1. **Что такое partitioning?** Разделение одной логической таблицы на несколько физических таблиц (партиций) по значению ключа. Приложение работает с родительской таблицей, а PostgreSQL сам кладёт строку в нужную партицию при вставке и выбирает нужные партиции при чтении.

2. **Чем partitioning отличается от индекса?** Индекс — дополнительная структура для быстрого поиска строк по условию. Как хранится таблица, он не меняет. Партиционирование меняет само хранение: данные разложены по отдельным таблицам. Это уменьшает объём чтения для запросов по ключу и позволяет обслуживать данные частями: удалить партицию, пройти `VACUUM` по одной партиции. Механизмы дополняют друг друга (часть 8).

3. **Какие стратегии partitioning поддерживает PostgreSQL?** RANGE (диапазоны), LIST (списки значений) и HASH (остаток от хэша). Для RANGE и LIST есть DEFAULT-партиция. Ключ может состоять из нескольких колонок или выражения, партиции можно партиционировать дальше (многоуровневое партиционирование).

4. **Когда использовать RANGE?** Когда ключ упорядочен, а запросы и жизненный цикл данных идут диапазонами: события, логи, заказы, платежи по дате. Архив и удаление старых данных делаются целыми партициями.

5. **Когда использовать LIST?** Когда ключ принимает небольшой заранее известный набор дискретных значений, а запросы фильтруют по равенству: тип клиента, страна, регион, tenant.

6. **Когда использовать HASH?** Когда нужно поделить большую таблицу на равные части, а естественных диапазонов и категорий нет, и запросы ищут по равенству ключа (`user_id = …`). Для запросов по диапазону и для удаления старых данных HASH не подходит.

7. **Как выбрать partition key?** Ключ должен:
   - стоять в условиях самых частых и тяжёлых запросов, иначе отсечения не будет;
   - не меняться — при изменении ключа строка переезжает в другую партицию;
   - быть `NOT NULL` и давать партиции сопоставимого размера;
   - соответствовать жизненному циклу данных (архив по времени).

   Кроме того, ключ обязан входить в первичный и уникальные ключи. Для `tasks` выбран `created_at` (часть 12).

8. **Что такое partition pruning?** Исключение из запроса партиций, в которых по их границам не может быть подходящих строк. При константах в условии это происходит при планировании: в плане остаются только нужные партиции (часть 2: 1 из 3). Для параметров, `now()` и подзапросов — при выполнении: `Subplans Removed` или `never executed` в плане.

9. **Почему pruning может не сработать?**
   - в условии нет ключа партиционирования (`event_type = 'click'`);
   - ключ обёрнут в функцию или приведение: `date(created_at) = …`, `created_at::date`;
   - условие по ключу стоит в `OR` с другими условиями;
   - типы в сравнении не совпадают;
   - отключён `enable_partition_pruning`.

   Кроме того, DEFAULT-партиция остаётся кандидатом для любых значений, которых нет в списках.

10. **Можно ли использовать индексы вместе с partitioning?** Да. Индекс, созданный на родителе, создаётся в каждой партиции, в том числе в будущих, которые создаст job. Уникальные индексы должны включать ключ партиционирования, глобального индекса на всю таблицу нет. Лучший результат даёт комбинация: pruning выбирает партицию, индекс находит строки в ней (часть 8: 8 буферов вместо 4 726).

11. **Что произойдёт, если подходящей партиции нет?** `INSERT` завершится ошибкой `no partition of relation "…" found for row` (SQLSTATE 23514), и данные не сохранятся. Если есть DEFAULT-партиция, строка попадёт в неё.

12. **Зачем создавать будущие партиции заранее?** Данные за новый день начинают поступать в 00:00:00, и партиция к этому моменту уже должна существовать. Создание партиции ненадолго блокирует родительскую таблицу, поэтому его лучше делать заранее и в тихое время. Запас в несколько периодов даёт время заметить сбой job и исправить его до того, как начнут падать вставки: при горизонте 3 дня на реакцию есть 3 дня.

13. **Почему создание партиций должно быть автоматизировано?** Календарь не останавливается, а человек забывает, болеет или уходит в отпуск. Ручная операция каждую ночь рано или поздно будет пропущена. Автоматическая job одинакова при каждом запуске, безопасна при повторе и пишет результат в лог. Но автоматизация тоже ломается, поэтому нужны ещё проверка и alert (часть 11).

14. **Чем логирование ошибки отличается от alerting?** Лог сохраняет факт для последующего разбора, но сам никого не зовёт: пока лог не прочитали, проблемы как бы нет. Alert активно сообщает ответственному человеку, что нужно действовать сейчас. У нас job пишет в лог каждый запуск, а alert отправляется только когда состояние становится CRITICAL или восстанавливается.

15. **Что такое recovery alert?** Сообщение о том, что проблема, о которой сообщали раньше, устранена. Оно закрывает инцидент: люди знают, что действовать больше не нужно. Без него нельзя отличить «проблему исправили» от «проверка сломалась и молчит».

16. **Почему нельзя бесконечно отправлять одинаковый alert?** Одинаковые сообщения каждые 5 минут быстро начинают игнорировать или отключают канал совсем — это «усталость от алертов». Тогда новая, настоящая проблема тонет в потоке. Кроме того, бесконечные сообщения упираются в лимиты канала. Поэтому уведомление отправляется при смене состояния (часть 11, задание 11.4).

17. **Всегда ли partitioning ускоряет запросы?** Нет. Он ускоряет запросы по ключу: в сервисе запрос за неделю со статусом ускорился с 297 до 3.8 ms. Запросы без ключа он не ускоряет и может замедлить: поиск задачи по `id` — 0.02 → 0.56 ms, статистика по всем задачам — 410 → 593 ms. С ростом числа партиций растёт время планирования (1 000 партиций — 12 ms). Кроме того, он добавляет ограничения: ключ входит в первичный ключ, внешние ключи на таблицу усложняются.

18. **Какие проблемы возникают при неправильном выборе размера партиций?** Слишком мелкие партиции (их слишком много) увеличивают время планирования и выполнения запросов без ключа — на 1 000 партиций 12 ms планирования и 97 ms выполнения против 0.14 и 32 ms на 10. Растут память под метаданные, число блокировок и файлов. Слишком крупные партиции почти не дают отсечения: запрос читает большую партицию целиком, `VACUUM` и перестроение индексов тяжёлые, старые данные удаляются слишком большими порциями. Неравномерные партиции создают «горячую» партицию, которая растёт и тормозит. Размер нужно выбирать так, чтобы типичный запрос читал одну или несколько партиций, а всего партиций было не больше сотен.

## Заключение

В работе на учебных таблицах изучены три стратегии партиционирования PostgreSQL. RANGE по дате и по цене отсекает партиции для запросов по диапазону: выборка за сутки читает одну треть данных, 4 726 буферов вместо 14 208. LIST отсекает по равенству, а DEFAULT-партиция страхует от неизвестных значений, но мешает создавать новые партиции и скрывает проблему. HASH распределил миллион строк по четырём партициям с отклонением не больше 0.15 процентного пункта, но плохо подходит для удаления старых данных. Измерения подтвердили, что партиционирование и индекс решают разные задачи: запрос по колонке вне ключа читает все партиции, пока нет индекса (41.6 → 7.4 ms).

В сервисе TaskManager реализована эксплуатационная часть:
- **CreatePartitionsJob** — идемпотентная задача, которая по конфигурации создаёт недостающие партиции на горизонт с запасом в один период и удаляет устаревшие;
- **PartitionHealthCheck** — проверка с HTTP-эндпоинтами и health check;
- **alert в Telegram** — отправляется один раз при сбое, повторно не дублируется, при восстановлении приходит recovery.

Сценарий «ночной job не отработал» проверен на работающем сервисе: удалённая партиция обнаружена, alert доставлен, после восстановления пришёл recovery.

Таблица `tasks` (5 млн строк) переведена на RANGE-партиции по месяцу `created_at`, для чего первичный ключ и внешний ключ связей с тегами расширены ключом партиционирования. Запросы API с периодом создания читают одну партицию из 30. Самый тяжёлый из них — неделя со статусом — ускорился в 78 раз, 297 → 3.8 ms. Запросы без ключа (по `id`, общая статистика) стали дороже, это цена выбранной схемы. Главный вывод работы: партиционирование — это не одна команда `PARTITION BY`, а жизненный цикл: выбор ключа по реальным запросам, создание партиций заранее, контроль их наличия и оповещение о сбое.
